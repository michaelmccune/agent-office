# OpenCode prompt-caching feasibility

**Checked 2026-11-07.** The `opencode` executable available during this research reports **1.19.5**. Agent Office does not pin an OpenCode version, so behavior can vary with the CLI installed by each operator. Version-specific OpenCode source links below are pinned to `v1.19.5`; provider documentation is rolling and was checked on the date above.

## Finding

**A shared, stable OpenCode system instruction can be added without merging it into each task prompt.** OpenCode 1.19.5 has an experimental `experimental.chat.system.transform` plugin hook, and its request builder sends system instructions separately from user messages. Agent Office already passes each task with `--prompt`. Its generated plugin can therefore add an office-wide instruction while leaving the queue/board/ask prompt task-specific.

**This can improve cache eligibility, but Agent Office cannot promise a cache hit, shared cache across workers, or lower total cost.** OpenAI, DeepSeek, and Z.AI each document automatic prefix caching for their own API; Anthropic also supports explicit cache breakpoints and OpenCode adds them for detected Claude routes. Actual reuse depends on the model, exact rendered prefix, request options, provider endpoint, account/organization, and cache lifetime. A cache write may cost more than uncached input on some models.

## Source-confirmed boundaries

- Agent Office launches a new OpenCode task with `--prompt` and resumes with `--session` in [`src/server/providers/opencode.ts`](https://github.com/michaelmccune/agent-office/blob/main/src/server/providers/opencode.ts). It merges the status plugin and optional MCP settings into `OPENCODE_CONFIG_CONTENT`, preserving the user's existing inline JSON, in [`src/server/opencode.ts`](https://github.com/michaelmccune/agent-office/blob/main/src/server/opencode.ts). It does not currently add office-wide prompt instructions there.
- The office's editable task, review, meeting, and queue prompt templates are described in [docs/agents.md](agents.md#the-offices-prompts). They are task/user-message content, not a shared system prompt.
- In OpenCode `v1.19.5`, `OPENCODE_CONFIG_CONTENT` is loaded as a config source ([`config.ts`](https://github.com/anomalyco/opencode/blob/v1.19.5/packages/opencode/src/config/config.ts)); the request builder keeps system instructions separate from user messages and supports a plugin system transform ([`request.ts`](https://github.com/anomalyco/opencode/blob/v1.19.5/packages/opencode/src/session/llm/request.ts), [`plugin/src/index.ts`](https://github.com/anomalyco/opencode/blob/v1.19.5/packages/plugin/src/index.ts)). A plugin also has `chat.params` to adjust provider request options. This is a real extension point, not a cache API shared by all vendors.
- OpenCode's v1.19.5 system context includes model identity, working directory, worktree, date, and possibly project references ([`system.ts`](https://github.com/anomalyco/opencode/blob/v1.19.5/packages/opencode/src/session/system.ts)). Tool schemas and model-specific instructions also participate in the rendered prompt. Different values or ordering can shorten the reusable prefix or invalidate it.
- OpenCode v1.19.5 automatically adds provider cache markers for Claude-compatible routes, and its provider transform normally derives `promptCacheKey` from the OpenCode session ID on certain SDK routes including OpenAI ([`transform.ts`](https://github.com/anomalyco/opencode/blob/v1.19.5/packages/opencode/src/provider/transform.ts)). Separate worker sessions therefore do not receive one shared OpenAI key by default. The same file shows that cache-marker behavior is provider-aware, not inferred from generic OpenAI compatibility.

## Provider and model support matrix

| Route / representative models | Cache behavior documented by the vendor | OpenCode 1.19.5 behavior and key control |
| --- | --- | --- |
| **OpenAI API** — current GPT models | Automatic prefix caching on supported models; newer Responses models also support explicit breakpoints and TTL options. | OpenAI SDK routes get a per-session `promptCacheKey` by default. The API accepts a caller-chosen `prompt_cache_key`, but OpenCode does not expose an office-wide shared key setting. OpenAI cache behavior does not apply automatically to a compatible proxy. |
| **DeepSeek API** — `deepseek-flash`, `deepseek-v4-pro` | Automatic disk-backed prefix caching; no request-side cache-control marker is needed. | No DeepSeek-specific cache marker or shared cache key is added by Agent Office/OpenCode. DeepSeek's `user_id` can isolate KV cache for privacy; it is not a documented shared cache key. |
| **Z.AI API** — GLM-5.3, GLM-5.2, GLM-4.7/4.6 | Z.AI documents implicit caching and cached-token usage for its own API. | OpenCode connects through an OpenAI-compatible SDK, but its generic compatibility does not create Z.AI cache behavior. Z.AI's own server-side caching works independently; its reviewed docs expose no cache key or TTL control. |
| **Anthropic API** — Claude | Explicit `cache_control` breakpoints and automatic caching; model-specific minimum length and TTL. | OpenCode adds ephemeral cache markers on detected Claude routes. An OpenAI-compatible proxy needs the right cache format configured; compatibility alone is insufficient. |
| **Google Gemini API** — Gemini 2.5+ | Implicit caching is automatic; explicit `cachedContent` resources are a separate managed-cache API. | No universal OpenCode cache key. Explicit resources need create/reference/expiry handling beyond an ordinary task prompt. |
| **OpenRouter** — multiple upstreams | Cache behavior and price depend on the selected upstream/model; OpenRouter adds provider-sticky routing. | Its `session_id` can steer requests to a provider endpoint for 60 minutes, but is an affinity hint, not a cache address or guarantee. OpenCode sends a per-session `X-Session-Id`; independent workers do not receive one shared Office ID. |
| **Other OpenAI-compatible endpoints / local servers** | Not inferable from the wire format. Vendor, model, and gateway must document caching separately. | OpenCode exposes provider/model request settings, but those can be ignored or rejected by the endpoint. No OpenAI cache claim should be applied to Ollama, vLLM, a proxy, or another compatible service without its own evidence. |

## Eligibility, cost, lifetime, and data handling

- **OpenAI:** The current guide sets a 1,024-visible-token minimum for GPT-5.6+; earlier-model minima depend on model and request settings. Prefix equality includes the rendered context and relevant settings such as model and tools. Newer Responses API cache writes default to a 30-minute minimum lifetime and cost 1.25× input; the 12-hour option costs 2.5×. Reads are discounted (commonly 0.1×, with model-specific rates); earlier models use model-dependent read prices and generally no extra write charge. Earlier-model cache entries typically last about 5–10 minutes of inactivity (up to an hour); 24-hour retention is available on selected models. OpenAI says caches are not shared across organizations or regional processing boundaries. It stores encrypted KV tensors on GPU-local machines, with no retention after 24 hours; this is distinct from the default up-to-30-day abuse-monitoring logs. A `prompt_cache_key` influences routing on pre-GPT-5.6 models but does not pin a machine or guarantee a hit; on newer models it is optional for routing and may separate cache accounting.
- **DeepSeek:** Its cache guide describes cache units at request boundaries, detected common prefixes, and fixed token intervals; a later request must fully match a persisted unit. Cache construction takes seconds and is best-effort. The guide gives no minimum prefix length or fixed TTL; it says unused disk cache is usually cleared within a few hours to a few days. Responses expose hit/miss token counts. As checked, the pricing page lists `deepseek-flash` cache-hit input at $0.003/$0.006 per million tokens off-peak/peak versus $0.15/$0.30 on a miss; `deepseek-v4-pro` at $0.022/$0.044 versus $0.66/$1.32. Rates can change. `user_id` isolates KV cache among different users under the same account; it is an isolation bucket, not a documented cache key or hit guarantee.
- **Z.AI:** Its guide says identical or highly similar repeated context may be cached and reports `usage.prompt_tokens_details.cached_tokens`; minor formatting can affect hits. It does not specify a minimum, TTL, invalidation schedule, or caller-controlled cache key. The pricing page checked lists GLM-5.3 input at $1.40/M tokens, cached input at $0.26/M, and cached-input storage as “Limited-time Free”; prices and promotions can change. Z.AI's API DPA says user-provided/generated content is processed in real time and not saved on its servers, while the caching guide does not describe cache retention or isolation separately. Treat the API agreement and endpoint's current terms as authoritative for deployment decisions.
- **Anthropic:** Cache writes are billed at 1.25× input for the default 5-minute TTL or 2× for 1 hour; reads are generally 0.1×, with model-specific rates. Minimum cacheable prompts vary from 512 to 4,096 tokens across active models; smaller prompts silently remain uncached. Changes before a breakpoint invalidate the matching suffix. Its ZDR documentation says cache KV representations and hashes remain in memory for the TTL and are promptly deleted afterward (with model-specific exclusions).
- **Google Gemini:** Current docs say implicit caching is on for Gemini 2.5+ and list minimums by model (2,048 tokens for Gemini 2.5 Flash/Pro; 4,096 for the listed Gemini 3/4 models). Implicit-cache TTL is not guaranteed in the reviewed guide. Explicit cached-content objects have a configurable TTL (1 hour by default), model-specific minimums, token and storage-duration charges, and can be listed for metadata or deleted; the cached content itself cannot be retrieved through the cache listing API. This is an explicit resource lifecycle, not a reusable `prompt_cache_key`.
- **OpenRouter and other gateways:** OpenRouter reports cached/read and write usage and uses a sticky upstream for 60 minutes after activity. Its session affinity is account-, model-, and conversation-scoped; changing the upstream, model, provider order, or session can change cache behavior. The upstream provider sets cache eligibility, TTL, and pricing. An `OpenAI-compatible` gateway can translate or drop cache fields, so verify its own contract and usage response.

Cache keys and explicit controls are not interchangeable. OpenAI's `prompt_cache_key` is an optional routing/accounting hint; DeepSeek's `user_id` is an isolation control; OpenRouter's `session_id` is an affinity/grouping key; Anthropic's `cache_control` and OpenAI's `prompt_cache_breakpoint` mark content boundaries; Google's `cachedContent` names an explicit server-managed resource, not a generic cache key. Anthropic's reviewed Messages docs do not specify cross-organization cache sharing, and Google's implicit cache does not expose a user key. None is a universal identifier that makes distinct provider accounts share cache state. Avoid placing credentials or secrets in a shared/cacheable instruction prefix.

## Recommendation and smallest next step

Proceed only as an **opt-in, best-effort OpenCode feature**. The smallest useful prototype is an admin-editable office-wide OpenCode system-instruction field that the Office plugin appends with `experimental.chat.system.transform`; retain `--prompt` unchanged for each task. The extension point exists in OpenCode 1.19.5, and the vendor-native automatic caches mean the first experiment needs no cache API abstraction. Use the existing OpenCode cache-read/cache-write usage snapshots to compare repeated tasks on the same model and account against a no-shared-prefix baseline.

Do **not** make a shared cache key the default. If measurement shows a miss problem for direct OpenAI models before GPT-5.6, a follow-up can opt into a stable `promptCacheKey` through `chat.params`, scoped to the provider/model, instruction revision, and the credential organization. Keep it disabled for unknown/compatible endpoints and when worker credentials or cache-isolation requirements differ. DeepSeek and Z.AI should initially use their native automatic behavior; neither reviewed API documents a caller-selected shared cache key. Do not promise a savings percentage or a hit rate: publish measured results by provider/model and retain an option to disable the shared prefix.

A provider-neutral production feature would need an Office config for the stable text and optional key scope, plugin hooks for system insertion and request options, and provider/model capability metadata for automatic versus explicit caching, accepted marker/key fields, minimum cacheable length, TTL, and cost. OpenCode's current model cost metadata does not express all those behaviors. Explicit cache requests also need provider-specific request shaping: OpenAI breakpoints/options, Anthropic `cache_control`, or Google's create/reference/delete cache-resource lifecycle. DeepSeek and Z.AI use their own automatic behavior. A generic OpenAI-compatible model must remain “unknown” until its endpoint documents support.
